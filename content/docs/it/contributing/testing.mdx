## Test Unitari (Vitest)

I test unitari coprono utility, logica di business, hook, componenti e il backend mock.

```bash
pnpm test              # modalità watch
pnpm test --run        # esecuzione singola
pnpm test:coverage     # con copertura
```

### File di Test

I test risiedono nelle directory `__tests__/` accanto al codice che testano:

```
apps/web/src/lib/__tests__/
  ├── budgets.test.ts
  ├── loan-buckets.test.ts
  ├── merchants.test.ts
  ├── net-worth.test.ts
  ├── amortization.test.ts
  └── ...
apps/web/src/lib/backend/__tests__/
  ├── adapter-contract.ts      # test contrattuali condivisi
  ├── mock.test.ts
  ├── mock.adapter.test.ts
  └── firebase.adapter.test.ts
```

### Backend Mock nei Test

Azzera lo stato del mock prima di ogni test:

```typescript
import { createMockAdapter, __resetMockState } from "../mock"

beforeEach(() => {
  __resetMockState()
  adapter = createMockAdapter()
})
```

### Test Contrattuali

`adapter-contract.ts` contiene i test che ogni adapter backend deve superare. Vengono eseguiti contro il mock a ogni `pnpm test`, e contro Firebase quando l'emulatore è attivo (`pnpm test:firebase:docker`). Un nuovo percorso di scrittura richiede un caso lì.

### Controllo della Documentazione

`apps/web/src/lib/__tests__/docs-check.test.ts` legge il README, `docs/` e queste pagine. Fallisce quando nominano un comando `pnpm` che non è uno script, un percorso del repository che non esiste o un link che non porta da nessuna parte.

## Test E2E (Playwright)

I test end-to-end coprono i flussi principali su una build di produzione con il backend mock, sulla porta 3001.

```bash
pnpm test:e2e
```

Il comando compila l'app e la avvia con `next start`. Per iterare in fretta, avvia prima un server di sviluppo su quella porta (`NEXT_PUBLIC_BACKEND=mock pnpm dev --port 3001`) e Playwright lo riusa invece di compilare. I test girano in Desktop Chrome, e un sottoinsieme anche in Mobile Chrome (viewport Pixel 5).

Gli spec sono in `apps/web/e2e/`, un file per area: `auth.spec.ts`, `dashboard.spec.ts`, `accounts.spec.ts`, `transactions.spec.ts`, `budgets.spec.ts`, `reports.spec.ts`, `mobile.spec.ts` e così via.

### Stati di Caricamento

Il mock risponde subito a ogni lettura, quindi uno stato di caricamento sparisce prima che un test lo veda. Per rallentarlo, uno spec imposta `window.__MOCK_LATENCY_MS__` (con `page.evaluate` o `page.addInitScript`) e ogni chiamata al database mock aspetta quel tempo. `loading-states.spec.ts` lo usa per verificare che nessuna pagina mostri uno stato vuoto prima dei dati.

### Pattern

- I test girano contro il backend mock per velocità e isolamento.
- Usa selettori basati sul ruolo e `aria-label`.
- Le interazioni solo desktop, come i menu hover, si testano nel viewport desktop.
