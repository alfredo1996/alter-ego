## Unit Tests (Vitest)

Unit tests cover utilities, business logic, hooks, components and the mock backend.

```bash
pnpm test              # watch mode
pnpm test --run        # single run
pnpm test:coverage     # with coverage
```

### Test Files

Tests live in `__tests__/` directories next to the code they test:

```
apps/web/src/lib/__tests__/
  ├── budgets.test.ts
  ├── loan-buckets.test.ts
  ├── merchants.test.ts
  ├── net-worth.test.ts
  ├── amortization.test.ts
  └── ...
apps/web/src/lib/backend/__tests__/
  ├── adapter-contract.ts      # shared contract tests
  ├── mock.test.ts
  ├── mock.adapter.test.ts
  └── firebase.adapter.test.ts
```

### Mock Backend in Tests

Reset the mock's state before each test:

```typescript
import { createMockAdapter, __resetMockState } from "../mock"

beforeEach(() => {
  __resetMockState()
  adapter = createMockAdapter()
})
```

### Contract Tests

`adapter-contract.ts` holds the tests any backend adapter must pass. They run against the mock on every `pnpm test`, and against Firebase when the emulator is up (`pnpm test:firebase:docker`). A new write path needs a case there.

### Documentation Check

`apps/web/src/lib/__tests__/docs-check.test.ts` reads the README, `docs/` and these pages. It fails when they name a `pnpm` command that is not a script, a repository path that does not exist, or a link that does not resolve.

## E2E Tests (Playwright)

End-to-end tests cover the main user flows against a production build with the mock backend, on port 3001.

```bash
pnpm test:e2e
```

This builds the app and starts it with `next start`. For quick iteration, start a dev server on that port first (`NEXT_PUBLIC_BACKEND=mock pnpm dev --port 3001`) and Playwright reuses it instead of building. Tests run in Desktop Chrome, and a subset also runs in Mobile Chrome (a Pixel 5 viewport).

The specs are in `apps/web/e2e/`, one file per area: `auth.spec.ts`, `dashboard.spec.ts`, `accounts.spec.ts`, `transactions.spec.ts`, `budgets.spec.ts`, `reports.spec.ts`, `mobile.spec.ts` and so on.

### Loading States

The mock answers every read at once, so a loading state is gone before a test can see it. To slow it down, a spec sets `window.__MOCK_LATENCY_MS__` (with `page.evaluate` or `page.addInitScript`) and every mock database call then waits that long. `loading-states.spec.ts` uses it to check that no page shows an empty state before its data.

### Patterns

- Tests run against the mock backend for speed and isolation.
- Use role-based selectors and `aria-label`.
- Desktop-only interactions, such as hover menus, are tested in the desktop viewport.
