## Overview

The Firebase backend uses Firestore for data storage and Firebase Authentication for user management.

## Data Model

Firestore uses a subcollection-based structure:

```
/categories (root — default categories)
/users/{userId}/
  ├── categories/
  ├── accounts/
  ├── transactions/
  ├── budgets/
  ├── savings_goals/
  ├── recurring_transactions/
  ├── tags/
  └── net_worth_snapshots/
```

## Configuration

```ini
NEXT_PUBLIC_BACKEND=firebase
NEXT_PUBLIC_FIREBASE_API_KEY=your-api-key
NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN=your-project.firebaseapp.com
NEXT_PUBLIC_FIREBASE_PROJECT_ID=your-project
NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID=123456
NEXT_PUBLIC_FIREBASE_APP_ID=1:123456:web:abcdef
```

## Key Implementation Details

- **Categories**: Merges root `/categories` (defaults) with user subcollection (custom)
- **Snapshots**: Uses `setDoc` with `{ merge: true }` and date-string doc IDs for idempotent daily snapshots
- **Loan payments**: `generateDue` mirrors mock logic including amortized principal/interest splits

## Security Rules

Firestore security rules should restrict each user's subcollection to their own `userId`. Root categories should be readable by all authenticated users.
